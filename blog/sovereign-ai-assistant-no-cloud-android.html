Sovereign AI: Run Your Own AI Assistant With Zero Cloud Dependency

Every mainstream AI assistant (ChatGPT, Google Gemini, Copilot, Claude) runs on someone else's hardware. Your queries are transmitted over the internet, processed on remote servers, and stored according to the provider's privacy policy. In most cases, you have no meaningful control over what happens to your data after it leaves your device.

Sovereignty means something different from toggling privacy settings. The model runs on your device, stores nothing off-device, and works without an internet connection. No vendor can revoke your access, throttle your usage, or pull the conversation logs for training. This guide explains how to build that on Android, the computer most people already carry everywhere.

The Four Pillars of AI Sovereignty

01
Local compute The model runs on your device's CPU/GPU/NPU. No API calls. No internet required for inference.
02
Local storage Model weights, conversation history, and memory are stored on your device. Nothing is uploaded.
03
Open weights The model's weights are openly licensed (Llama, Gemma, Mistral, Phi). You can inspect, fine-tune, or replace them.
04
Open runtime The inference engine is open source (llama.cpp, MLC-LLM, Ollama). No black-box SDK required to run it.

Why Android Specifically?

Android phones are the most capable portable computers most people own. A 2023-era flagship has a Snapdragon 8 Gen 2 with a dedicated NPU capable of 26 TOPS — fast enough to run a 4B parameter model at conversational speeds. And unlike iPhones, Android lets you sideload apps, install package managers like Termux, and run background services with full control.

The fact that you already carry it everywhere means your sovereign AI goes everywhere with you — no need to pull out a laptop or connect to a server.

Model Selection: What Actually Runs Well on a Phone

Not every open-weight model is practical on a phone. You need a quantized model small enough to fit in RAM while leaving headroom for other apps.

  • Gemma 4B Q4_K_M (~2.5 GB) — Google's model, excellent instruction following, runs at ~15 tok/s on SD 8 Gen 1. Best balance of quality and speed for conversational use.
  • Llama 3.1 8B Q3_K_S (~3.5 GB) — Meta's model, stronger at reasoning and coding. Tight fit on 6 GB devices; comfortable on 8 GB.
  • Phi-4 Mini 3.8B (~2.2 GB) — Microsoft's small model, exceptional at math and logical reasoning relative to its size.
  • Mistral 7B Q2_K (~2.7 GB) — If you want the best raw language quality at 7B with maximum compression.
Quantization matters: Q4_K_M is the sweet spot: about 25% quality loss vs FP16, but 4x smaller. Q2_K is smaller still but noticeably degraded. For a 4B model, Q4_K_M is almost always the right choice.

The Manual Route: Termux + llama.cpp

If you want complete control (specific model, specific quantization, custom system prompts, local API access):

# 1. Install Termux from F-Droid (not Play Store)
# 2. In Termux:
pkg install clang cmake git python

# 3. Build llama.cpp
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp && mkdir build && cd build
cmake .. -DGGML_OPENMP=ON -DGGML_VULKAN=ON  # Vulkan = GPU acceleration
make llama-server -j4

# 4. Download a model (example: Gemma 4B Q4_K_M)
pip install huggingface_hub
huggingface-cli download google/gemma-4b-GGUF gemma-4b-q4_k_m.gguf \
  --local-dir ~/models/

# 5. Start the inference server
./llama-server -m ~/models/gemma-4b-q4_k_m.gguf \
  --host 127.0.0.1 --port 11434 \
  --n-gpu-layers 20 --ctx-size 4096

The server runs at http://localhost:11434 and is API-compatible with Ollama, so any Ollama-compatible app can use it as a backend. Your queries never leave the device.

Adding Memory and Context Persistence

A sovereign AI should remember things across sessions. LLMs are stateless; they forget everything when the context window ends. You need an external memory layer.

Shadow AI handles this via ShadowMemoryCore: a local SQLite database on-device that stores named memories, retrieves relevant ones at prompt time, and injects them into the system context. No cloud sync. No vector database subscription. Pure local SQLite.

For the Termux route, you can build something similar: store conversation summaries in SQLite, retrieve recent ones and prepend them to the system prompt at each session start.
